# ADR-003: Data residency и изоляция PII

**Статус**: Принято · Этап 1
**Контекст**:
- Пользователи по всему миру; данные о здоровье (ЧСС, SpO2) —
  специальная категория GDPR (Art. 9); дети — особый режим
  (особенность 5, NFR-04, FR-15).
- АК-2 (приватность) — один из трёх основных атрибутов ([А-08](../../stage1-concept/08-quality-attributes.md)).
- Риск T-05: утечка PII через логи/аналитику.

**Решение**:
1. **Residency**: персональные данные пользователя хранятся только в
   регионе его проживания (PostgreSQL региона, PII-хранилище региона).
   «Регион» определяется при регистрации и меняется только через
   миграционный сценарий.
2. **Отдельное PII-хранилище**: персональные поля (имя, почта, история
   согласий, возрастной флаг, биометрия) живут не в доменных БД, а в
   изолированном хранилище под KMS с отдельными ключами; домены хранят
   только `user_id` и получают PII по явному запросу с журналом доступа.
3. **Согласия как данные**: каждое согласие (маркетинг, биометрия,
   видимость «сейчас») — версионированная запись; отозвал = события
   очистки во все домены (ADR-004).
4. **Кросс-облачно уходят только обезличенные события** (агрегаты,
   псевдонимы) — для аналитики и ML.
5. Логи и метрики: PII-фильтр на агенте до отправки (ADR-012).

**Последствия**:
- (+) Выгрузка/удаление (GDPR Art. 15/17) — сборка пакета из одного
  места: целевой срок 7–30 дней (КС-7).
- (+) Область инцидента утечки — только PII-хранилище под ключами.
- (−) Дополнительное обращение в тёплых путях (профиль, настройки):
  компенсируется кэшем BFF с коротким TTL.
- (−) Сложность миграции между регионами — описана как отдельный
  сценарий, редкий (переезд пользователя).
- (−) ML-персонализация работает на обезличенных признаках — требует
  дисциплины в схемах событий.
