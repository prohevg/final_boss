# ADR-009: Единая идентичность — OIDC/SSO с приложениями компании

**Статус**: Принято · Этап 1
**Контекст**:
- FR-10: интеграция с существующими приложениями; у компании уже есть
  аккаунтная база покупателей — второй «независимый» вход создал бы
  дубли профилей и злые пароли.
- АК-2/NFR-04: токены, step-up, возрастной режим; T-10 — компрометация
  ключей.
- B-03: приложения компании — внешняя зависимость с их SLA.

**Решение**:
1. **Единый IdP компании по OIDC** (authorization code + PKCE на
   мобильном): SportSphere — доверенный клиент; вход «по покупательскому
   аккаунту» + соцсети/аноним (под аккаунт привязывается).
2. **Токены**: access — 15 минут (JWT, проверка JWKS на шлюзе —
   ADR-005); refresh — с ротацией и обнаружением кражи (revocation-список).
3. **Step-up аутентификация** для чувствительных операций: покупка
   (переход в магазин с атрибуцией), изменение приватности, выгрузка
   данных — повторное подтверждение (биометрия/PIN).
4. **Возрастной режим**: дата рождения → флаг «несовершеннолетний»;
   включает урезанные настройки видимости и отдельное согласие
   законного представителя (FR-15, NFR-04).
5. **Отдельные ключи партнёров** (приложения компании как интеграторы):
   mTLS + подписанные запросы, ротация, квоты (ADR-010) — не через
   пользовательские токены.
6. Идентичность хранится в Identity-домене; остальные домены получают
   только `user_id`/клеймы по событию (ADR-004) — PII не копируется.

**Последствия**:
- (+) Один вход для пользователя всех приложений компании (Ц-4),
  нет второго пароля, профиль покупок связывается легально.
- (+) Единая точка для отзывов и step-up — АК-2.
- (−) Зависимость от IdP компании (B-03): кэш JWKS, локальный режим
  «валидация по кэшу» при недоступности IdP ≥ 1 ч (сессии не рвутся),
  деградация входа — приоритет инцидента.
- (−) Сложность миграции анонимных пользователей в аккаунт: сценарий
  «привязка после первой синхронизации» — офлайн-данные не теряются.

(проверка на шлюзе), ADR-010 (ключи партнёров), ADR-003 (PII в Identity);
риск T-10, B-04.
