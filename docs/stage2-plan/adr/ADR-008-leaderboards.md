# ADR-008: Live-лидерборды в Redis, история в ClickHouse

**Статус**: Принято · Этап 1
**Контекст**:
- КС-1: во время соревнования тысячи участников обновляют позиции;
  обновление таблицы на экране ≤ 10 с (АК-1).
- FR-02: сравнения «с собой / регионом / профи» — исторические срезы
  по миллионам тренировок.
- T-11: аномалии (некорректный ЧСС, GPS-скачки) не должны портить
  рейтинги.

**Решение**:
1. **Live-слой — Redis ZSET**, ключ = соревнование/период, score
   обновляется атомарным `ZINCRBY` (никакого read-modify-write).
   Шардирование по `participant_id % N`; горячий топик соревнования —
   выделенный слот-кластер с TTL на время события + окно медали.
2. **Обновления в Redis** идут из Kafka (ADR-004) одним потребителем
   на ключ — порядок гарантирован, дубли схлопываются по `event_id`.
3. **Исторические сравнения — ClickHouse**: срезы «регион/профи/период»,
   личные рекорды, агрегаты для Insights; накопление из тех же событий
   (отдельный consumer, независимый от live).
4. **Валидация до рейтинга**: поток проходит правила (плоскость GPS,
   разумность темпа, доверие к источнику устройства) — подозрительное
   помечается и в leaderboard попадает с пометкой «на проверке»,
   из глобальных таблиц исключается до модерации.
5. Диффузия в UI: подписка WebSocket → пакет изменений раз в 10 с
   (не чаще одного сообщения клиенту в секунду).

**Последствия**:
- (+) Пик ×10 обрабатывается атомарными инкрементами без блокировок;
  стоимость live — только на время события (TTL), не постоянно.
- (+) История и live независимы: падение ClickHouse не влияет на
  соревнование, и наоборот (АК-1).
- (+) ClickHouse дешёв в анализе: срезы по 100+ млн строк — секунды.
- (−) Redis — состояние в памяти: кластер с репликами и AOF,
  «прогрев» лидерборда после отказа из Kafka (история перечитывается) —
  допустимо, т.к. итоги фиксируются и в ClickHouse.
- (−) Два хранилища одного рода данных (live vs история): сверка
  итогов соревнования — сверочный джоб после события (те же деньги
  в ADR-004 для атрибуции).
