# ADR-004: Событийная интеграция через Kafka

**Статус**: Принято · Этап 1
**Контекст**:
- Домены должны релизоваться независимо (ADR-001): синхронные вызовы
  связывают их версии и судьбы.
- Пики соревнований ×10 должны «впитываться» без отказов (АК-1, T-02).
- Порядок событий одного пользователя критичен (статистика, очки).
- Практика `10.5`: очереди как основа устойчивости; `9.6`: событийное
  моделирование и агрегаты.

**Решение**:
1. **Kafka — единственный способ междоменного обмена** в горячем пути
   (кроме BFF-сборки экранов). Каждый домен публикует события своей
   темы; подписки — через consumer groups.
2. **Ключ партиционирования — `user_id`**: гарантирует порядок событий
   одного пользователя; шардов по нагрузке.
3. **Семантика — at-least-once + идемпотентность на приёме** (упор:
   дедуп по `event_id`, версионные upsert'ы). Выбор против exactly-once:
   дешевле и достаточно для статистики/уведомлений; денежные пути
   (атрибуция покупок) сверяются сверкой (reconciliation-джоб).
4. **Буферизация**: всплески пиков держит очередь Kafka, потребители
   растут по lag (KEDA) — приём не блокируется (см. КС-1).
5. Схемы событий — версионируются (Avro/JSON-schema registry),
   обратная совместимость обязательна (контроль в CI).
6. Кросс-облачная доставка — через Kafka-хаб (MirrorMaker),
   домены читают «свой» регион (ADR-002).

**Последствия**:
- (+) Независимые релизы, пиковый буфер, аудит (история событий),
  реиграбельность (новый потребитель = пересчёт из истории).
- (+) Масштабирование потребителей независимо от продюсеров.
- (−) Вторичная доставляемость: дубли возможны → дисциплина
  идемпотентности (закреплена в шаблоне сервиса, проверяется тестами).
- (−) Консистентность «в конце транзакции»: UI показывает оптимистичный
  результат, сверка — асинхронно (терпимо для соцсценариев; для
  покупок — сверка ADR-010).
- (−) Оверхед эксплуатации кластера Kafka — ADR-011 (где self-managed).
