# ADR-002: Мультиоблачность и портируемое ядро

**Статус**: Принято · Этап 1
**Контекст**:
- Контекст задания: 90 % систем в облаке, **нет единого провайдера** —
  используется тот, что лучше подходит задаче.
- Риск T-01 ([А-05](../../stage1-concept/05-risks.md)): разные
  managed-сервисы и дрейф конфигураций дороже, чем кажется.
- NFR-11: запрет vendor lock-in в ядре; NFR-09: отказ региона.

**Решение**:
1. **Ядро портируемо**: доменные сервисы — контейнеры; инфраструктура —
   Terraform-модули с общим интерфейсом; деплой — единый GitOps-контур
   (ArgoCD/подобный) поверх K8s в каждом провайдере.
2. **Запрет SDK провайдера в доменах**: специфика провайдера — только в
   адаптерах инфраструктуры (S3-совместимое хранилище, Postgres-
   совместимые БД, управляемые Redis/Kafka с общими коннекторами).
3. **Распределение ролей**: провайдер A — основные регионы EU/US;
   провайдер B — APAC + резервный контур EU (DRP из практики 14.5).
   Глобальный контур (Kafka-хаб, бэкапы) — в обоих.
4. Модель расширения: новый регион = новый workspace Terraform + узел
   GitOps, без изменения кода доменов.

**Последствия**:
- (+) Независимость от прайса/выхода провайдера; выбор «best-of-breed»
  под задачу сохранён (как требует контекст).
- (+) Отказ провайдера = переключение GSLB + DRP (риск T-08 закрыт).
- (−) Управляемые сервисы берём только те, что есть в обоих облаках в
  сопоставимом виде, либо self-managed (ADR-011) — иногда это дороже.
- (−) Двойной контур эксплуатации: закрывается единым GitOps и ADR-012;
  стоимость — в [А-16](../../stage3-risk-cost/16-tco.md) (сравнение
  «2 облака против 1»).
- (−) Кросс-облачная латентность: домены не ходят синхронно между
  провайдерами в горячем пути (только события через хаб, ADR-004).
