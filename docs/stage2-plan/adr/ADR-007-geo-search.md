# ADR-007: Гео-поиск людей и маршрутов на OpenSearch

**Статус**: Принято · Этап 1
**Контекст**:
- FR-03: поиск по общим интересам, месту, маршрутам и «тренируются
  прямо сейчас» — гибридный запрос: гео + фасеты + полнотекст + real-time
  статус (КС-5).
- NFR-01: ответ ≤ 500 мс.
- ADR-003: residency — индекс должен жить в регионе пользователя.

**Решение**:
1. **OpenSearch (geo-плагин)** как основной движок поиска людей, мест
   и маршрутов: geo_bounding_box/geo_distance, фасеты (интересы,
   уровень, доступность), «сейчас» — отдельный свежий слой
   (тернарный индекс со статусом TTL).
2. **Индекс обслуживает домен Search** и наполняется из событий
   (ADR-004): профиль, друзья, маршруты, активные сессии — публикуют
   изменения в топик, Search инкрементально обновляет индекс (read model).
3. **Резерв**: для точечных запросов («мой маршрут», «друзья рядом»)
   остаются PostGIS-запросы к PostgreSQL региона — без OpenSearch
   сервис не встаёт, функция деградирует до узкой (fallback).
4. Индексы по регионам (residency); свежий слой «сейчас» — в Redis
   (TTL на сессию) с фоновым синхронизацией в индекс для выборок.

**Последствия**:
- (+) Один движок закрывает три разных поиска (люди/места/маршруты)
  и укладывается в 500 мс на гео-запросах.
- (+) Read model не нагружает оперативные БД доменов (поиск — только
  чтение индекса).
- (−) Дополнительный кластер в каждом регионе (стоимость — строка
  «Поиск» в А-16).
- (−) Консистентность индекса со вторичной задержкой (до секунд) —
  для «сейчас» критично: слой Redis отвечает мгновенно, индекс догоняет.
- (−) Операционная сложность: закрывается SRE-шаблоном кластера,
  мониторинг — ADR-012.

**Связи**: ФТ FR-03, КС-5; [А-14b](../views/information.md)
(представление данных поиска); NFR-01; ADR-004 (наполнение),
ADR-008 (параллельный realtime-слой в Redis).
