# ADR-005: API-шлюз и BFF как единая точка входа

**Статус**: Принято · Этап 1
**Контекст**:
- Три типа клиентов (мобильное приложение, приложения компании,
  внутренние воркеры) с разными потребностями в контрактах.
- NFR-01 (отзывчивость), NFR-02 (доступность), T-10 (атаки/переборы).
- Практика `13.5`: шлюзы по типу коммуникации (проверено на схемах).

**Решение**:
1. **Один глобальный API-шлюз** перед всеми доменами: TLS-терминация,
   проверка JWT (JWKS), rate limit и квоты (на пользователя и на
   партнёра), анти-бот/анти-скрейпинг правила, маршрутизация.
2. **Два BFF**: мобильный (сборка экранов лент/статистики: 3–5 вызовов
   доменов → 1 ответ, агрегация в кэше) и партнёрский (узкий публичный
   контракт для приложений компании — не раскрываем внутренние домены).
3. BFF — единственное место склейки данных нескольких доменов;
   доменные API не публикуются наружу.
4. WebSocket-канал (лидерборды, «сейчас») выходит через отдельный
   realtime-шлюз с теми же токенами и квотами на соединение.
5. Версионирование контрактов: `/v1`, декадационное окно ≥ 2 версий
   (нужно приложениям компании — ADR-010).

**Последствия**:
- (+) Единая точка контроля (безопасность, квоты, аудит) — закрывает
  T-10 и поддерживает АК-2.
- (+) Клиенты не знают топологию доменов → независимые релизы (ADR-001).
- (+) BFF уменьшает число запросов и латентность экранов (NFR-01).
- (−) Шлюз — критичная точка: балансируем redundancy в регионе,
  локальный кэш конфига, деградация «кэш → без кэша» (NFR-02).
- (−) BFF может разрастись «серым ядром»: правила — в BFF только
  агрегация и формат, бизнес-логика остаётся в доменах (контроль на
  ревью).
